Claude · 13:35

Yes. shell-bc-load already covers this, though no skill has a ready-made "torsion test" mode or a twist-angle report. You set it up as a case:

"supports": [{"edge": "x0", "dofs": [1,1,1,1,1,1]}, {"rigid_end": "xL"}],
"loads":    [{"node": {"rigid": "xL"}, "moment": [T, 0, 0]}],
"analysis": {"type": "linear"},
"report_node": {"rigid": "xL"}
  • Applying the torque: {"rigid_end": "xL"} ties the tip section to one master node, and "moment": [T,0,0] puts the torque on that node about the beam axis (x). You can also spread it along the free edge with {"edge": "xL", "moment": [T,0,0]}. The skill's own notes say curved sections should be loaded through a rigid end rather than a free edge.
  • Reading the twist: collect_results saves all 6 DOFs (ux uy uz rx ry rz) for every node in the results .npz, and that includes the rigid-end master node (shell_bc_load.py:305). The twist angle is rx of that node: look up its tag in meta["rigid"]["xL"], then read disp[:, 3] for that node. Torsional stiffness is then GJ_eff = T·L / rx.
  • Large twist: use "corotational": true with load_control. displacement_control with "dof": 4 should also work, prescribing tip rotation and reading back the torque as the load factor. One caution: the shell-buckling notes say the rigid link used here (rigidLink + Transformation) holds only for small rotations and fails under rotation control. For large twists, shell-buckling provides sb.rigid_end, a corotational-beam fixture.

Hand check: shell_buckling.py computes thin-walled section properties for any cross-section, including St Venant J, the warping constant Cw and the shear centre. You can compare the FE twist with TL/(GJ). For open sections such as tape springs, the clamped root restrains warping, so expect the FE beam to come out stiffer than the St Venant value unless it is long compared with sqrt(EC_w/GJ).

Gaps: no skill reports twist directly or compares it with a torsion formula. The regression tests also include no torsion case, so this load path hasn't been verified the way bending has. I can write a small driver script that runs the case and prints the twist and GJ against the closed-form value.

Claude · 15:55

This is a bug in the comparison tool, .claude/verification/compare_results.py, not in either model. It only affects the stress comparison on the doubled webs.

What goes wrong: the tool matches stresses by layer number and position within the layer (bottom, middle or top), not by height through the wall. The two models split the 0.2 mm web into layers differently:

  • OpenSees treats the web as two bonded tapes, each 0.1 mm thick. The skills mirror the tape and stack it under itself. So the web has two plies:
  • ply 1 runs from z = −0.1 to 0 mm;
  • ply 2 runs from z = 0 to +0.1 mm.

"Ply 1, top" is therefore z = 0, the bond line at the middle of the wall. - Abaqus gets the web as one homogeneous 0.2 mm layer, because the material is isotropic. Its section points run from −1 to +1 across the whole thickness, and section_point_map labels the +1 point "layer 1, top". That point is z = +0.1 mm, the outer surface.

The tool then pairs "layer 1, top" from each code. That compares Abaqus' outer surface with OpenSees' mid-thickness: - Under torsion and bending the mid-thickness stress is close to zero. This produced the "~0 in OpenSees" CHECK lines. - Comparing a surface value with a near-zero one also produced the false "factor 2 (tensor vs engineering?)" warning. - In the parity plots it shows as the vertical streak of points at OpenSees ≈ 0.

How we know it's only the tool: - Both times, the agent recomputed the OpenSees web stress at z = +0.1 mm itself and found it agrees with Abaqus' surface point. In the nonlinear run the shear stress matched to within about 3.4%, consistent with every other field. - The flanges are unaffected because they are one layer in both codes. - Displacements, strains, curvatures and section forces don't depend on this pairing, so they're unaffected too.

The fix is small: pair section points by height through the wall (each point's fraction × h/2) instead of by layer number. In particular, a single-layer Abaqus section's top and bottom points should map to the top of OpenSees' last ply and the bottom of its first ply. Neither agent edited the tool. If you want it fixed, I'd do it after the shell-bc-load torsion change I'm working on now, and re-run the verification tests in .claude/verification/test_verification.py.
